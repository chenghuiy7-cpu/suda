\begin{abstract}
Fully homomorphic encryption (FHE) accelerators act as ciphertext consumers, substantially reducing the cost of homomorphic computation. However, producing their inputs from persistent data and processing returned results introduce additional overhead. Conventionally, the host serves as the input producer, using CPU and memory resources for data access, preprocessing, encryption, and buffering. It also decrypts returned results and writes them back to storage. Moreover, ciphertext expansion further increases buffering and data-movement costs.

We present FHEStore, an FPGA-based computational storage system that bridges persistent data and FHE accelerators through storage-side input production and result postprocessing. FHEStore combines storage-side data access with an FPGA streaming datapath to integrate lightweight preprocessing and Fast Fully Homomorphic Encryption over the Torus (TFHE). On the return path, it decrypts results on the FPGA and writes the decrypted results back to persistent storage.

We prototype FHEStore on an FPGA-enabled computational storage device and integrate it with a remote homomorphic processing unit (HPU). For TFHE encryption of unsigned 8-bit data with a batch size of 4~KiB, the FPGA encryption engine achieves a $5.33\times$ speedup over host CPU-based encryption. In the evaluated end-to-end input production workflow, FHEStore achieves a $3.26\times$ speedup over the host-based baseline. We also demonstrate homomorphic computation on the remote HPU using FHEStore-generated ciphertexts.
\end{abstract}

\section{Introduction}
\label{sec:introduction}
Fully homomorphic encryption (FHE) enables a data owner to outsource computation over encrypted data without revealing the plaintext to the evaluator. For applications backed by persistent data, using an FHE accelerator involves two paths around homomorphic computation. An input producer accesses application data and generates the ciphertexts that the accelerator consumes. On the return path, result ciphertexts are decrypted and the recovered values are written back to storage. Input production and result postprocessing thus connect persistent application data with encrypted computation, and their costs remain part of the application workflow.

Dedicated hardware research addresses the execution cost of plaintext--ciphertext conversion through specialized encryption and decryption architectures~\cite{mert2020bfv,lee2023ckks,feryputri2025lwe,syafalni2026multicore}. Specialized arithmetic and parallel datapaths make cryptographic conversion a practical acceleration target across FHE schemes. Translating that acceleration into an application benefit also requires connecting the operators to data preparation, ciphertext delivery, and result recovery. The cost of those surrounding stages depends on where conversion is placed and how data are handed between stages.

Research on memory-aware FHE accelerators complements arithmetic acceleration by optimizing data reuse, memory access, and traffic during homomorphic computation~\cite{xu2026hera,zhou2023fhemem,vanbeirendonck2023fpt,kim2022bts,kim2022ark}. This work establishes the expanded ciphertext representation and large cryptographic working sets, including evaluation keys, as architectural concerns alongside arithmetic. The resulting data layouts, memory organizations, and streaming schedules improve the execution of homomorphic programs. Their optimization boundary centers on the working set consumed by encrypted computation. Application workflows additionally need to generate input ciphertexts from persistent data and convert returned ciphertexts into persistent results; organizing these paths is a complementary systems problem.

Client-side systems further combine cryptographic acceleration with encoding, memory organization, streaming, buffering, or client--server communication~\cite{krieger2024aloha,yune2025abcfhe,vanderhagen2022choco,gupta2024memfhe}. Their client-side processing paths connect cryptographic stages to memory or communication interfaces. For applications whose inputs and outputs reside in persistent storage, the design boundary also encompasses data access and preprocessing before encryption, as well as result write-back after decryption. Integrating these stages with conversion extends the coordination problem from client processing to persistent-data input production and result postprocessing.

This broader boundary couples cryptographic execution with host resource use. In a conventional host-based workflow, CPU software reads and preprocesses stored plaintext, encodes and encrypts the values, and stages ciphertexts for accelerator delivery. It also decrypts returned ciphertexts and writes the recovered values back to storage. Host memory holds plaintext, ciphertexts, and intermediate buffers across these stages; ciphertext expansion increases the volume handled at their interfaces. Offloading encryption and decryption moves their cryptographic computation off the host CPU, while the placement and coordination of the operators determine the buffering and data handoffs required around them. Our objective is therefore to accelerate TFHE encryption and decryption while reducing host CPU work, host-memory buffering, and intermediate data movement between persistent storage and FHE accelerators. Meeting this objective requires jointly designing cryptographic operators and their placement within the input and return paths.

We present FHEStore, an FPGA-based computational storage system that integrates cryptographic acceleration with storage-side input production and result postprocessing. FHEStore implements TFHE encryption and decryption~\cite{chillotti2020tfhe} as hardware operators using high-level synthesis (HLS), with plaintext encoding integrated into encryption. The input streaming datapath connects storage-side data access and lightweight preprocessing to FPGA ciphertext generation. The return datapath connects FPGA decryption of returned ciphertexts to persistent result write-back. A control path coordinates operator execution and data handling, supporting an application workflow from persistent inputs through ciphertext handoff to recovered-result write-back.

\section{Background and Motivation}
\label{sec:background}
\subsection{FHE and TFHE Fundamentals}
FHE provides key generation, encryption, homomorphic evaluation, and decryption~\cite{gentry2009fhe}. Let $k_{\mathrm{enc}}$, $k_{\mathrm{dec}}$, and $k_{\mathrm{eval}}$ denote the scheme's encryption, decryption, and evaluation key material. For messages $m_1,\ldots,m_t$, form $c_i\leftarrow\operatorname{Enc}_{k_{\mathrm{enc}}}(m_i)$ and $c_f\leftarrow\operatorname{Eval}_{k_{\mathrm{eval}}}(f,c_1,\ldots,c_t)$. With valid parameters, an exact scheme satisfies the following relation for a supported computation $f$, with overwhelming probability over its randomness:
\begin{equation}
  \operatorname{Dec}_{k_{\mathrm{dec}}}(c_f)=f(m_1,\ldots,m_t).
  \label{eq:fhe-correctness}
\end{equation}
Encoding maps application values into the scheme's message representation; decoding maps decrypted messages back into application values.

TFHE operates over the torus $\mathbb{T}=\mathbb{R}/\mathbb{Z}$ and uses learning-with-errors (LWE) and ring-based ciphertexts, with bootstrapping to control noise during homomorphic computation~\cite{chillotti2020tfhe}. A representative building block is secret-key torus-LWE encryption. Let $\mu=\operatorname{Encode}(m)$ belong to a discrete message space $\mathcal{M}\subset\mathbb{T}$, and let $\mathbf{s}\in\mathbb{Z}^{n}$ be the secret key. Sampling a uniform mask $\mathbf{a}\in\mathbb{T}^{n}$ and an error $e$ from the scheme's noise distribution yields the ciphertext
\begin{equation}
  c=(\mathbf{a},b),\qquad
  b=\langle\mathbf{a},\mathbf{s}\rangle+\mu+e\pmod{1}.
  \label{eq:torus-lwe-encryption}
\end{equation}
Decryption computes the ciphertext's phase,
\begin{equation}
  \phi_{\mathbf{s}}(c)=b-\langle\mathbf{a},\mathbf{s}\rangle
  =\mu+e\pmod{1},
  \label{eq:torus-lwe-phase}
\end{equation}
and recovers the nearest element of $\mathcal{M}$ under the torus distance before decoding the application value. Recovery succeeds when the phase remains within the encoded message's decision region~\cite{chillotti2020tfhe}.

These operations expose distinct tasks for hardware: encoding, randomness generation, and key-dependent accumulation on encryption; phase recovery and decoding on decryption. In this torus-LWE representation, a ciphertext contains $n+1$ coefficients. Its serialized size depends on the coefficient precision and cryptographic parameters, while the number of ciphertexts needed for application data depends on the encoding. These choices determine both the cryptographic workload and the volume handled by buffers and transfer interfaces.

\subsection{Existing FHE Producer--Consumer Workflows}
Outsourced FHE systems commonly place encoding, encryption, decryption, and decoding in the data owner's trusted domain, while a server performs homomorphic computation~\cite{krieger2024aloha,yune2025abcfhe,gupta2024memfhe}. We describe this organization through a producer--consumer view: the input producer prepares ciphertexts, the evaluator consumes them to execute an encrypted program, and the owner recovers the returned results. The evaluator receives the ciphertexts and any required evaluation material, while the decryption key remains within the owner's trusted domain.

Existing implementations realize these roles through different processing and memory interfaces. Client-side accelerators connect encoding and cryptographic conversion to software control, local memory, or external-memory transfers~\cite{krieger2024aloha,yune2025abcfhe}. FHE computation accelerators schedule encrypted operations over ciphertexts and evaluation keys supplied to their memory systems~\cite{xu2026hera,zhou2023fhemem,vanbeirendonck2023fpt}. Across this boundary, the producer and consumer must agree on cryptographic parameters, message encoding, and ciphertext layout. Client-aided execution can also introduce intermediate exchanges in which the client decrypts, processes, and re-encrypts values before computation resumes~\cite{vanderhagen2022choco}.

For the persistent-data workload considered here, input production begins with stored application data and includes access and preprocessing before encoding and encryption. Result postprocessing recovers application values through decryption and decoding and writes them back to persistent storage. Storage access, cryptographic conversion, and accelerator communication consequently form connected stages. Their interfaces determine where plaintext and ciphertext batches are buffered, how work is submitted, and when results become available to the application. This workflow provides the system context for placing conversion alongside persistent-data access.

\subsection{Computational Storage and Application Integration}
Computational storage couples processing with storage to offload host work or reduce data movement~\cite{snia2025csmodel}. By executing operations along the storage-access path, it can process data where they are stored or accessed, instead of requiring host software to perform every transformation after a conventional read. The processing interface connects persistent data to an executable task, with task completion coordinated with the surrounding application.

Typical operations include filtering, statistical aggregation, feature selection, and decompression~\cite{ruan2019insider}. These operations combine storage access with application processing: a read can deliver selected or transformed data, and a write can incorporate processing before data are stored. The benefit depends on the operation and its output representation. Filtering can shrink the returned data, whereas a representation-changing operation can produce a larger output.

Application integration requires abstractions for accessing data, configuring processing, and obtaining results. FPGA storage frameworks provide examples through virtual-file access, C++ interfaces with data and parameter streams, and unified HLS interfaces for memory and storage~\cite{ruan2019insider,wong2024dongle}. Such interfaces allow application code to express processing tasks and data access while the framework coordinates transfers and hardware execution. Usability therefore depends on how the system exposes task parameters, input and output locations, and completion semantics alongside the processing operators.

This combination of data access and programmable processing suits the FHE workflow described above. On the input path, storage access and preprocessing can feed encoding and encryption; on the return path, decryption and decoding can feed result write-back. Encryption expands the representation, so operator placement determines the intermediate handoffs and buffering around the required ciphertext exchange. Integrating cryptographic operators with storage-side streams and application control is the basis of FHEStore's architecture, presented in Section~\ref{sec:architecture}.

\section{System Overview}
\label{sec:architecture}

FHEStore connects persistent-data access to storage-side input production and result postprocessing. Its input path connects storage access and optional preprocessing to FPGA encoding and TFHE encryption; its return path connects FPGA decryption and decoding to result write-back. The host coordinates CSD execution and ciphertext handoffs to and from the external consumer.

\subsection{System Organization}
\label{subsec:system-organization}

Figure~\ref{fig:pipeline} shows the system boundaries and the control and data paths. FHEStore comprises an FPGA-based computational storage device (CSD) and the host software that coordinates its operators and ciphertext handoffs. The remote server represents an external prototype for privacy-preserving outsourced computation with a homomorphic accelerator. The CSD combines persistent storage, device-local buffers, a device runtime, and an FPGA operator pool. The input producer reads stored data, applies lightweight preprocessing when requested, and supplies application values to encoding and encryption. On the return path, decryption and decoding recover application values for persistent write-back.

The host coordinates application control and ciphertext communication. Its task runtime submits device work and receives execution completion. Its ciphertext relay retrieves generated ciphertexts from the CSD and stages returned ciphertexts for the CSD's decryption path. PCIe carries task submission, completion, and ciphertext transfers between the host and CSD; the host connects the relay to the external service over a network.

Following the producer--consumer organization in Section~\ref{sec:background}, FHEStore assumes that the host and CSD belong to the data owner's trusted domain. Input plaintext, recovered results, and secret-key material are handled within this domain. The host loads the LWE secret key $\mathbf{s}$ locally and supplies it to the CSD's cryptographic operators through their execution contexts.

\subsection{Application Task Model}
\label{subsec:application-task}

An application specifies a task $T=(D,Q,E,O)$. $D$ identifies the stored input and its record schema. $Q$ specifies selection predicates and projected fields when preprocessing is requested. $E$ identifies the encoding and cryptographic parameter preset. $O$ specifies ciphertext delivery or an outsourced operation and a destination for recovered results. These descriptions express the application request independently of device endpoints, batch sizes, and transfer settings chosen by the runtime.

For example, a selective-update task can read a range of records, select those satisfying predicates over integer fields, and encrypt a projected unsigned 8-bit field. The task also specifies where the recovered values should be written after the outsourced operation.

For a selective task, let $r_0,\ldots,r_{N-1}$ denote the source records. The predicate in $Q$ selects $M$ records, and $\pi_Q$ projects their chosen field. Let $\mathcal{I}_Q=(i_0,\ldots,i_{M-1})$ list their indices in source order. With configuration $E$ and local secret key $\mathbf{s}$, the input producer emits
\begin{equation}
  c_j \leftarrow \operatorname{Enc}_{\mathbf{s},E}\!\left(
    \operatorname{Encode}_{E}\!\left(\pi_Q(r_{i_j})\right)
  \right),\quad 0\leq j<M.
  \label{eq:task-ciphertexts}
\end{equation}
Here, $c_j$ denotes the ciphertext bundle representing one application value. Encoding produces the message blocks for that value, and encryption applies to each block using the LWE representation in Equation~\ref{eq:torus-lwe-encryption}. The host retains $\mathcal{I}_Q$ alongside the ciphertext sequence. For an elementwise update, the $j$th returned value corresponds to record $i_j$, allowing result postprocessing to place it in the selected field of that record.

\subsection{Operator Graphs and Device Execution}
\label{subsec:operator-execution}

The task runtime translates $T$ into an operator program, operator contexts, and input and output memory ranges. The program specifies operator types and their stream connections. Contexts carry the record layout from $D$, selection and projection settings from $Q$, and cryptographic configuration from $E$. Memory ranges bind an invocation to device-local buffers and byte extents. The host submits these objects to the device runtime, which configures FPGA execution.

For selective input production, the graph connects filtering and projection directly to encoding and encryption, keeping their data handoff inside the CSD. The selected count and the per-value ciphertext size specified by $E$ determine the generation program's output extent. The selected record indices provide the mapping $\mathcal{I}_Q$ used for result placement. Tasks without preprocessing use a single cryptographic operator.

The output action $O$ determines how execution proceeds after ciphertext generation. For tasks that invoke outsourced computation, the host relays generated ciphertexts to the external service and transfers returned ciphertexts into the input range of a separate CSD decryption program. FPGA decryption and decoding produce recovered application values in its output range. For contiguous outputs, the device copies this buffer to the designated SSD range. For selected-record updates, the host uses $\mathcal{I}_Q$ to merge recovered values into destination record pages while preserving unselected records and other fields.

Completion is reported to the application when the output requested by $O$ is available. A generation-only task completes with its ciphertexts and, when selection is used, its record mapping; an update task also waits for result recovery and destination I/O.

\label{sec:conclusion}
FHEStore bridges persistent data and FHE accelerators through FPGA-based computational storage. Its input path combines storage-side data access, lightweight preprocessing, and TFHE encryption; its output path decrypts returned result ciphertexts on the FPGA and writes the decrypted results to persistent storage.
